# Canonical Research Record — MSS Locker Single-Page Workspace

Date: 2026-09-04. Audience: client/product/engineering. Scope: static repository audit, supplied screenshot, build/tests, and authoritative web guidance. Geography: current Indian INR/GST-oriented application; no legal compliance conclusion. Assumption: “single page” means one persistent workspace without full document navigation, while preserving addressable state.

Direct answer: use a URL-driven, permission-filtered workspace shell with lazily loaded modules, visibility-gated queries, contextual inspectors and task dialogs. Do not extend the 856-line Dashboard into a giant eager page.

## Deposits and refunds module audit — 2026-09-04

The embedded module mixed a dark standalone dashboard with the light continuous workspace, exposed financial actions without UI permission affordances, and selected the first ledger row's allocation for new operations. That was a material mis-posting risk and failed on an empty ledger. The implementation now requires an explicit active customer-locker account, passes that ID to collect/adjust/refund flows, filters actions using authenticated permissions, replaces the refund-cancellation browser prompt with an audited confirmation form, and aligns cards, controls and tables with the light workspace.

Accessibility decisions retain native HTML tables with captions and scoped headers. Loading/success/error feedback has programmatic status semantics, icon-only destructive actions have accessible names, and states use labels rather than color alone. Sources: W3C WAI ARIA APG Table and Grid Patterns, accessed 2026-09-04, https://www.w3.org/WAI/ARIA/apg/patterns/table/ and https://www.w3.org/WAI/ARIA/apg/patterns/grid/; WCAG Understanding Status Messages and Non-text Contrast, accessed 2026-09-04, https://www.w3.org/WAI/WCAG22/Understanding/status-messages and https://www.w3.org/WAI/WCAG22/Understanding/non-text-contrast. Authoritative standards guidance; high confidence.

Validation: frontend TypeScript and production Vite build passed. The shared application bundle remains about 526 kB minified and triggers Vite's existing size warning; the deposits/refunds lazy chunk is about 82 kB (15 kB gzip). No backend contract or schema changed. Limitations: no live role matrix, populated production dataset, browser automation, screen-reader session, or user observation was available.

## Collect deposit modal audit — 2026-09-04

Repository inspection found that overcollection was visually gated but not conditionally authorized on the server: `/deposits/collect` required `deposits.collect`, while `allowOverride` was trusted without checking `deposits.override`. It also found unused backend idempotency support, no non-cash reference requirement, and an overlay without modal focus management. The implementation adds server-side override authorization, per-flow idempotency headers, non-cash reconciliation validation, labelled native radio inputs, responsive light styling, explicit transaction review, text errors, focus containment, Escape handling and focus restoration.

The interaction decisions follow the W3C WAI ARIA APG Dialog (Modal) Pattern, accessed 2026-09-04, https://www.w3.org/WAI/ARIA/apg/patterns/dialog-modal/, which calls for a named modal, focus inside it, contained Tab navigation, Escape closing and focus return. Form feedback follows WCAG 2.2 Understanding Error Identification and Labels or Instructions, accessed 2026-09-04, https://www.w3.org/WAI/WCAG22/Understanding/error-identification and https://www.w3.org/WAI/WCAG21/Understanding/labels-or-instructions.html. Visible focus follows WCAG 2.2 Understanding Focus Visible, updated 2026-07-12 and accessed 2026-09-04, https://www.w3.org/WAI/WCAG22/Understanding/focus-visible. All are authoritative W3C guidance; high confidence.

Verification: frontend production build passed; backend build plus 7 unit and 3 integration tests passed. No schema changed. Limitations: no live browser interaction, assistive-technology session, real payment-rail reconciliation policy, or role fixture was available. Requiring a reference for every non-cash method is a product-risk control inferred from the application's reconciliation fields, not a cited regulatory requirement; confirm it with the client.

## Locker closure module audit — 2026-09-04

Repository inspection found two UI identity/authorization mismatches: the page read `user.role.permissions` rather than AuthContext's effective `permissions`, and `user._id` rather than the typed `user.id`. It also found a server authorization gap where `overrideFinancial` was accepted without enforcing the defined `closures.financial_override` permission. The implementation corrects both UI inputs, adds server enforcement, exposes the approved release queue in summary statistics, distinguishes API failure/first-use/filtered-empty states, improves native table semantics, and portals closure dialogs to the viewport.

The four-stage request/review/approve/release presentation is an application-specific synthesis of the existing backend state machine, not an externally prescribed banking process. Status presentation was informed by the GOV.UK Design System Task List, accessed 2026-09-04, https://design-system.service.gov.uk/components/task-list/. Sequential operability and result/error announcements follow W3C WCAG Understanding Focus Order, Error Identification and Status Messages, accessed 2026-09-04, https://www.w3.org/WAI/WCAG22/Understanding/focus-order, https://www.w3.org/WAI/WCAG22/Understanding/error-identification and https://www.w3.org/WAI/WCAG22/Understanding/status-messages. These sources support interaction/accessibility decisions, not legal or regulatory claims.

Verification: frontend production build passed; backend build, 7 unit tests and 3 integration tests passed. No schema migration was required. Limitations: no seeded end-to-end status fixtures, production role matrix, operations-staff observation, browser automation, or assistive-technology session was available. The existing server state transition and transactional completion logic were inspected but not redesigned.

## Restored workspace section navigator — 2026-09-04

The prior five-item control was restored at the boundary between executive KPIs and continuous module content. Because all target sections remain visible, representing this control as an ARIA tablist would communicate a false selected-tab/controlled-panel model. It is implemented as a labelled in-page `nav` with hash links, permission filtering, current-location indication, IntersectionObserver active-state tracking, horizontal mobile overflow and sufficient scroll margin below the sticky application/navigation bars.

This decision follows W3C WAI guidance that navigation helps users understand where they are and move elsewhere, and that `nav` creates a navigation landmark for groups of links: “Understanding Guideline 2.4: Navigable” and “Landmark Regions,” accessed 2026-09-04, https://www.w3.org/WAI/WCAG22/Understanding/navigable and https://www.w3.org/WAI/ARIA/apg/practices/landmark-regions/. Descriptive section headings and logical sequential focus are supported by “Understanding Headings and Labels” and “Understanding Focus Order,” accessed 2026-09-04, https://www.w3.org/WAI/WCAG22/Understanding/headings-and-labels and https://www.w3.org/WAI/WCAG22/Understanding/focus-order. Authoritative accessibility guidance; high confidence.

Verification: frontend TypeScript and production Vite build passed before the final scroll-margin adjustment; a final build is recorded with the implementation handoff. No API or schema changed. Limitation: active-section behavior was structurally verified but not browser-automated at multiple viewport heights.

## Unified operations page hardening — 2026-09-04

The full-page audit found a fixed 1,500-record vault cutoff, request-per-keystroke customer search, faux KPI controls, globally invalidated queries, permission-agnostic local CTAs, errors presented as empty datasets, and visible table/detail actions connected to no-op callbacks. The implementation now uses the repository's pagination-safe compact locker loader with abort propagation, a 300 ms search debounce, native KPI buttons, local permission gates, scoped refresh, retryable error states, and optional transactional handlers that render only when implemented.

Interaction guidance comes from W3C WAI-ARIA APG Button Pattern and Keyboard Interface, accessed 2026-09-04, https://www.w3.org/WAI/ARIA/apg/patterns/button/ and https://www.w3.org/WAI/ARIA/apg/practices/keyboard-interface/. Failure feedback follows WCAG 2.2 Understanding Status Messages, accessed 2026-09-04, https://www.w3.org/WAI/WCAG22/Understanding/status-messages.html. Request cancellation and targeted cache refresh follow TanStack Query's Query Cancellation and Query Invalidation guides, accessed 2026-09-04, https://tanstack.com/query/latest/docs/framework/react/guides/query-cancellation and https://tanstack.com/query/latest/docs/framework/react/guides/query-invalidation. These are authoritative standards or primary framework documentation; confidence high.

Verification: frontend TypeScript and production Vite build passed. Vite's existing shared-bundle warning remains at approximately 526 kB minified, while large downstream workspace modules remain lazy-loaded. No API or schema changed. Limitations: no browser automation, populated role matrix, assistive-technology session, production analytics, or production database profiling was available.

## Record Payment Collection modal — 2026-09-04

The repository audit found an impossible `OTHER` payment flow (server-required reference with no UI field), an unreachable success/receipt screen in the unified dashboard because the parent unmounted the modal on submit, loss of invoice context when paying from a dossier, a zero-balance fallback to total invoice value, silent/racy invoice search, hidden stale method references in payloads, and incomplete dialog semantics. The implementation fixes those contracts while retaining the existing server-side idempotency lookup, MongoDB transaction and live outstanding-balance reconciliation.

Dialog focus containment, Escape behavior and focus return follow the W3C WAI-ARIA APG Dialog (Modal) Pattern, accessed 2026-09-04, https://www.w3.org/WAI/ARIA/apg/patterns/dialog-modal/. Explicit errors and associated labels follow WCAG 2.2 Understanding Error Identification and Labels or Instructions, accessed 2026-09-04, https://www.w3.org/WAI/WCAG22/Understanding/error-identification.html and https://www.w3.org/WAI/WCAG22/Understanding/labels-or-instructions.html. RFC 9110 section 9.2.2, accessed 2026-09-04, https://www.rfc-editor.org/rfc/rfc9110.html#section-9.2.2, supports the general retry/idempotency rationale; the custom `Idempotency-Key` behavior is a repository-specific contract. HTML date constraint behavior was checked against MDN's date input reference, accessed 2026-09-04, https://developer.mozilla.org/en-US/docs/Web/HTML/Reference/Elements/input/date.

Verification: frontend TypeScript and production Vite build passed. No API or schema changed. Limitations: no populated end-to-end invoice fixture, browser automation, screen-reader session, real payment-rail integration or finance-team usability session was available.
